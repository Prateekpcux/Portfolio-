The result

The Problem

One-off dashboards. Trust slipping.

Across Inova's clinical analytics work, I partnered with clinical leaders, BI developers, analysts, and executives to make dashboards easier to use and easier to trust.

The fix wasn't a prettier chart. It was a shared way to build every dashboard — one any team could follow without me.

What was breaking

Built in isolation.

  • Different layouts, filters, and labels everywhere
  • What a number actually meant wasn't always shown
  • Hard to connect what we do → results → cost
  • Developers rebuilt the same thing again and again
  • When dashboards looked different, people trusted them less
What I built

One shared way to build them.

  • Ran workshops to agree on what "good" looks like
  • Built a design system in Figma made for Tableau
  • Designed clear number patterns, filters, and built-in notes
  • Made a simple path from request to finished dashboard
  • Wrote it down so any team can follow it
How I Worked

Vague requests in. Clear standards out.

A clear path turned fuzzy dashboard requests into reusable standards. Every step left something behind — nothing lived only in someone's head.

What I Learned

Three things shaped everything.

Through workshops, dashboard reviews, and stakeholder sessions, the same patterns kept showing up. Each one became a pillar of the system.

📐

Make them consistent

Same layout, same way of showing key numbers, same filters — across every team. Learn one dashboard, and you know them all.

📖

Make them explain themselves

People needed dashboards to point out what matters, not just show more numbers. Context was missing nearly everywhere.

🔒

Make them trustworthy

Where the data comes from, when it updates, who owns it — all easy to find. Without that, people didn't trust what they saw.

Working Sessions

12+ sessions. No decision made alone.

We met often with analysts, developers, and clinical teams to check requirements, agree on what each number means, and compare layouts — all before any code was written. Catching problems early is the cheapest time to fix them.

The Design System

A shared kit of parts for every dashboard.

The system gave every team the same building blocks — spacing, type, color, key-number styles, built-in notes, filters, and layout. Built in Figma, checked against what Tableau can actually render, and written down so developers can build from it without a designer next to them.

The Review Process

How every dashboard gets built now.

A simple, repeatable path means the standards apply to every dashboard the team builds — not just the ones I designed. Same five steps, every time, request to launch.

Step 1

Request

What's the need, who's it for, what decision does it support?

Step 2

Discover

Find the metrics and decisions it has to support.

Step 3

Wireframe

Agree on the layout before any building starts.

Step 4

Review

Check it against the standards with clinical and BI.

Step 5

Build

Build it with the approved parts and patterns.

The Result

The system outlasts any one project.

The win wasn't a single dashboard. It was giving teams a shared way to build, review, and ship — so the quality holds up long after I move on.

This showed how UX can matter beyond a single screen. By combining workshops, a design system, dashboard design, and a simple review process, I helped clinical and BI teams make analytics that's easier to understand, easier to build, and easier to trust. The most lasting work wasn't any one dashboard — it was the shared way of working that lets teams build better ones without me in the room.

What made it hard

The challenge wasn't the visuals.

The hard part was getting clinical, BI, and leadership to agree on what each number even means — they all defined the same metric differently. The design system forced that conversation early, before anyone wrote a line of Tableau.

The takeaway

The system is the product.

The most lasting work here wasn't a screen. It was the shared standards and process that let many teams build better dashboards on their own — with less rework and more trust. That keeps paying off in a way a single deliverable can't.
